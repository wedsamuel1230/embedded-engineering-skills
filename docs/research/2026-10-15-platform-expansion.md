# Platform expansion research: Zephyr, STM32Cube, Pico SDK, and MicroPython

**Research date:** 2026-10-15. Scope is a practical build/debug skill proposal for macOS host workflows. The commands below build artifacts on the host; they do not flash hardware or establish electrical/functional behavior.

## Recommendation

Add four small, independently selectable skills with one deterministic build fixture each. Keep CI/build and hardware validation as separate evidence. Suggested fixtures: Zephyr `native_sim` (host executable, no board), STM32CubeF4 on PlatformIO `nucleo_f401re` (cross-compiled ELF), Pico SDK for RP2040 (CMake cross-compiled ELF/UF2), and MicroPython Unix port (host executable plus REPL). The skills should teach diagnosis from compiler/linker output and artifacts and only enter hardware debug after a board, probe, wiring, and toolchain are actually present.

## Fixture prerequisites and boundaries

- **Zephyr on macOS:** Python 3, an isolated Python environment with `west` and the checked-out release's Python requirements, CMake, Ninja, device-tree compiler, and a host C/C++ compiler. Bootstrap using the release-specific [getting-started guide](https://docs.zephyrproject.org/4.4.1/develop/getting_started/index.html); `west sdk install` installs cross toolchains for hardware targets, while the proposed `native_sim` fixture uses the host simulator path. Pinning only the Zephyr Git revision is insufficient for reproducibility: record the `west` version, Python version/lock, host compiler, CMake/Ninja, and workspace module revisions (`west update` state) in the fixture report. `west build` does not flash; `west flash` is a separate target operation. |
- **STM32Cube via PlatformIO:** use a minimal `platformio.ini` with exact `platform = platformio/ststm32@19.7.1`, `board = nucleo_f401re`, `framework = stm32cube`, and exact `platform_packages` overrides above. Required packages include the cross-compiler and the F4 framework; add exact package pins for every package the fixture actually resolves. PlatformIO's board lists on-board ST-LINK and debug support; this is capability metadata, not proof a probe is connected. A raw STM32Cube CMake fixture would need an explicit startup/vector table, linker script, HAL/CMSIS source closure, and compiler toolchain file, so it is a larger maintenance surface than this PlatformIO fixture. ST's official CubeF4 repository also uses git submodules and requires recursive clone; its board examples are preconfigured for several vendor IDEs, not one universal CMake project. [ST STM32CubeF4 repository](https://github.com/STMicroelectronics/STM32CubeF4). |
- **Pico SDK:** macOS host tools include CMake, Ninja or Make, and `arm-none-eabi-gcc` plus newlib; use official SDK's `external/pico_sdk_import.cmake`, `PICO_SDK_PATH`, and `pico_sdk_init()`. Clone the selected tag and initialize submodules. Use a tiny UART/stdout or GPIO-independent compile fixture, avoiding claims about pin function or actual output. Build command: `cmake -S . -B build -DPICO_SDK_PATH="$PICO_SDK_PATH" -DPICO_BOARD=pico -DCMAKE_BUILD_TYPE=Debug -G Ninja`; then `cmake --build build`. `pico_add_extra_outputs(target)` emits `.elf`, `.uf2`, `.bin`, and `.hex` as applicable. UF2 generation still does not mean a board was programmed. Debugging teaches ELF symbols/map and GDB/OpenOCD/SWD boundary; SWD requires probe, target, and wiring. |
- **MicroPython Unix:** macOS requires Xcode Command Line Tools/Apple Clang, GNU Make, Git, and Python 3. The `minimal` variant disables almost all optional modules, avoiding the default `standard` variant's `pkg-config`/`libffi` dependencies; the tag's port README documents both paths and output directory. Build `mpy-cross` only when testing frozen/compiled Python modules; it is not needed for the Unix minimal interpreter. A Unix-port REPL can reproduce language/runtime and many library-level issues, but not MCU pin APIs, UART/I2C/SPI electrical transactions, timing, or board-specific exceptions. `mpremote` uses serial transport to a real MicroPython board and should be taught in a distinct device-connected procedure, with `mpremote` itself pinned in the project's Python lock. |

## Debugging coverage worth teaching

1. Capture exact tool versions, target/board, clean-build command, first failing diagnostic, and build directory before changing code. Distinguish configuration/generation, compile, link, and post-build conversion failures.
2. Preserve and inspect ELF, map, size output, linker script, and symbols. For ARM targets, use the matching `arm-none-eabi-gdb` with a compatible probe server such as OpenOCD/ST-LINK; separate “ELF was built” from “GDB attached” and from actual runtime observations. For faults, reason from captured PC/LR/xPSR and fault registers only when a real target dump/log exists.
3. Treat I2C/SPI/UART triage as a measurement workflow: check selected peripheral/pinmux, clock/divider, address/CPOL/CPHA/word size, pull-ups and voltage levels from the actual design/datasheet, then compare a logic-analyzer or scope capture with software logs. A successful build or host simulator cannot establish bus levels, ACKs, signal integrity, or wiring.
4. For MicroPython, distinguish the host Unix REPL (language/runtime reproduction) from `mpremote repl` on a serial-connected device. The latter proves a transport session only; sensor/peripheral claims still need code and physical measurements.

## Skill-discovery finding

The official OpenAI Skills documentation defines a skill as a folder containing `SKILL.md` and optional supporting folders, and describes making a directory available for discovery; the Agent Skills format specifies the skill-directory shape and relative references. These standards do **not** establish that all hosts recursively discover category-nested skill folders. The Codex sample describes each skill as a folder and `$CODEX_HOME/skills` as the discovery destination, but does not promise recursive category traversal. Cursor's official docs explicitly say Cursor recursively scans nested folders; that behavior is host-specific. [OpenAI Skills guide](https://developers.openai.com/api/docs/guides/tools-skills), [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx), [Codex skill creator sample](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/skill-creator/SKILL.md), [Cursor Skills docs](https://cursor.com/help/customization/skills).

**Portable structure:** retain actual skill bundles flat at `skills/<skill-name>/SKILL.md`. Category folders such as `catalog/<category>/README.md` can be navigational indexes, but should not contain undiscoverable skill bundles as the only copy. Provider adapters should expose explicit paths/copy/install mappings in each manifest or install script; do not assume recursive search. This matches this repo's existing statement that provider manifests are adapters and the canonical skill content is under `skills/`.

## Source/reproducibility notes

- Commit IDs were obtained from the upstream Git tag refs (`git ls-remote`) on the research date. For Zephyr, the annotated tag object is `247e755247840abefa16136168b4a56682150f50`; peeled source commit is the one listed above. Other listed refs resolve directly to their source commits.
- PlatformIO v19.7.1's upstream `platform.json` declares broad package version ranges. Therefore pinning only `platform` is not a fully frozen build. The F4 framework override is set to 1.28.1 rather than the newer 1.28.3 returned by the registry on this date, keeping within the platform's declared `~1.28.1`; pin toolchain separately and capture all resolved package versions. PlatformIO registry's current toolchain listing includes 1.120301.0.
- The cited docs support these commands and workflow boundaries, but this research did not install toolchains, run builds, attach a debugger, flash a board, or measure electrical behavior.
